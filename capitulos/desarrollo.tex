\section{Generación Procedural de Colisionadores (Optimización)}
Para que las herramientas de interacción mediante trazado de rayos (\textit{Raycast}), como el escáner espacial o el puntero de selección, operen de forma precisa sobre el modelo BIM, es necesario que cada elemento geométrico posea un volumen de colisión (\texttt{MeshCollider}). Configurar esto de forma manual en modelos arquitectónicos complejos que contienen miles de piezas resulta inviable.

Para automatizar este proceso, se desarrolló el componente \texttt{ModelOptimizer}. Durante la inicialización de la escena (\texttt{Start}), este algoritmo emplea una corrutina (\textit{Coroutine}) para iterar de forma asíncrona sobre todos los componentes \texttt{MeshFilter} del modelo importado. Al detectar una malla visual carente de físicas, instancia dinámicamente un \texttt{MeshCollider} y le transfiere la topología exacta de la pieza (\texttt{sharedMesh}). La ejecución se ha escalonado empleando \texttt{yield return null} cada diez iteraciones; esta técnica de programación concurrente garantiza que el hilo principal (\textit{Main Thread}) no se congele durante el procesamiento de edificios de alta densidad poligonal, manteniendo los fotogramas por segundo estables al cargar el entorno.



\section{Alineación Espacial de Modelos (BIM vs Realidad)}
Para que la validación y el escáner de desviaciones funcionen correctamente, es necesario que el modelo teórico BIM y la reconstrucción volumétrica (Gaussian Splatting) compartan exactamente el mismo sistema de coordenadas globales. Dado que las capturas de la realidad suelen generarse con orígenes y rotaciones arbitrarias, se ha desarrollado el script \texttt{AlineadorModelos} para automatizar la superposición precisa de ambos entornos.

El sistema emplea un algoritmo de emparejamiento basado en tres puntos de referencia homólogos (anclas) definidos tanto en el BIM como en la realidad:
\begin{itemize}
    \item \textbf{Punto 1 (Origen):} Define la traslación exacta entre ambos mundos.
    \item \textbf{Punto 2 (Dirección Forward):} Establece el vector de profundidad.
    \item \textbf{Punto 3 (Dirección Up):} Ayuda a definir el plano y la verticalidad.
\end{itemize}

Matemáticamente, el script calcula los vectores directores (\texttt{forward}) y los vectores normales (\texttt{up}) utilizando el producto vectorial (\texttt{Vector3.Cross}) entre los puntos definidos. Con estos datos, se generan cuaterniones de rotación (\texttt{Quaternion.LookRotation}) para ambos espacios. Posteriormente, se calcula la diferencia rotacional multiplicando la rotación del BIM por la inversa de la rotación real (\texttt{Quaternion.Inverse}). Finalmente, esta diferencia de cuaterniones se aplica a la rotación del modelo escaneado, pivotando sobre el primer punto de anclaje para alinear geométricamente ambos mundos con precisión milimétrica como se puede observar en la Figura \ref{fig:alineador}.

\section{Detección Automática de Colisiones (Clash Detection)}
Una de las fases más críticas en la coordinación BIM es la identificación de interferencias entre las instalaciones (MEP) y los elementos arquitectónicos o estructurales (Figura \ref{fig:MEP-struct}). Para automatizar este proceso en el entorno virtual, se ha implementado el módulo \texttt{BIMClashDetector}.

El algoritmo evalúa las colisiones mediante la intersección de cajas delimitadoras (\textit{Axis-Aligned Bounding Boxes} o AABB). Para evitar falsos positivos causados por roces superficiales (elementos que están en contacto pero no se atraviesan de forma crítica), el sistema reduce los límites de los colisionadores (\texttt{Bounds.Expand(-toleranciaConflicto)}) basándose en una variable paramétrica. Si tras esta substracción las áreas se siguen intersecando (\texttt{Intersects}), se confirma un conflicto estructural (\textit{Hard Clash}).

Al detectar una interferencia, el sistema ejecuta tres acciones automatizadas:
\begin{enumerate}
    \item Instancia procedimentalmente un marcador visual (esfera roja) en el centro exacto de la colisión, calculado a partir del promedio espacial de la superposición de los límites.
    \item Registra el impacto en la matriz de datos global para su posterior volcado en el sistema de informes (\texttt{GeneradorPDF}).
    \item Se comunica directamente con la arquitectura de capas (\texttt{BuildingLayerManager}) enviando un conjunto de datos (\texttt{HashSet}) con las piezas involucradas. El gestor de capas aísla automáticamente estos elementos, ocultando el resto del edificio para proporcionar al usuario una vista limpia del problema.
\end{enumerate}

\section{Sistema de Visualización Dual (Gestión de Modelos)}
La aplicación permite al usuario alternar dinámicamente entre el modelo de diseño teórico (BIM) y la captura de la realidad física (Gaussian Splatting). Esto es fundamental para identificar discrepancias en la obra mediante la superposición de ambos entornos.

Para gestionar esta funcionalidad, se ha desarrollado el script \texttt{LayerSwitcher}. Este componente utiliza una máquina de estados sencilla basada en un enumerado personalizado llamado \texttt{ViewMode}, el cual define tres estados lógicos posibles:
\begin{itemize}
\item BIM: Solo se renderiza la malla FBX.
\item GaussianSplat: Solo se renderiza la nube de puntos volumétrica.
\item Both: Superposición activa de ambos modelos simultáneamente.
\end{itemize}
El script se ejecuta en el \texttt{Update()} escuchando las entradas de los controladores de Realidad Virtual (específicamente el botón X del mando izquierdo, mapeado mediante la API \texttt{OVRInput.GetDown()}). Al detectar una pulsación, el sistema recalcula qué modelo debe ser visible y utiliza el método \texttt{SetActive(true/false)} de Unity para habilitar o deshabilitar la raíz de la jerarquía de los objetos correspondientes.

Cabe destacar que para el renderizador de Gaussian Splatting, se incluyó una línea de código específica para forzar la recarga del componente (\texttt{GaussianSplatRenderer.enabled = true}) para asegurar que el buffer gráfico de la GPU se actualiza correctamente al volver de un estado inactivo.

Como se puede apreciar en la Figura~\ref{fig:layer-switcher-unity}, la integración en Unity se realizó creando un objeto vacío (\textit{Empty GameObject}) en la jerarquía principal llamado \texttt{[LayerManager]}. A este objeto se le añadió el script \texttt{LayerSwitcher} como componente. Finalmente, desde el panel Inspector, se arrastraron físicamente los objetos contenedores del modelo BIM y de la nube de Gaussian Splatting a los huecos de las variables públicas declaradas en el script, estableciendo así las referencias en memoria necesarias para su control. \section{Sistema de Punteros e Interacción Base}
En un entorno de Realidad Virtual, el usuario necesita una referencia visual constante de hacia dónde están orientados sus controladores físicos para poder apuntar e interactuar con menús u objetos distantes. El objetivo es proyectar un rayo que sirva como "puntero láser".

Para esta funcionalidad se ha implementado el script \texttt{ControllerRayVisual}. A diferencia de otros sistemas que dependen de entradas globales, este script se basa en la jerarquía de Unity:

Utiliza un componente \texttt{LineRenderer} adjunto al mismo objeto para dibujar una línea poligonal continua en el espacio 3D.
En cada frame (\texttt{Update()}), el script accede a la propiedad \texttt{transform.position} del mando físico estableciéndola como origen (índice 0 de la línea). Para el punto final (índice 1), calcula un vector proyectado sumando a la posición inicial el vector de dirección \texttt{transform.forward} multiplicado por una variable escalar de distancia (por defecto, 10 metros).
A nivel de código, se ha forzado la propiedad \texttt{lineRenderer.useWorldSpace = true} con el objetivo de asegurar que los vértices de la línea se calculen sobre las coordenadas globales de la escena, evitando que el rayo rote sobre sí mismo de forma errática cuando el jugador mueve la muñeca.


En la integración en Unity se localizó el objeto \texttt{LeftControllerAnchor} (generado por el rig de cámaras de Oculus dentro de \texttt{TrackingSpace}). Se le adjuntó el script creado y un componente \texttt{LineRenderer}. En las propiedades del \texttt{LineRenderer}, se ajustó el \texttt{Width} (grosor) a un valor de \texttt{0.005} metros para simular un láser fino. Por último, se le asignó un material de tipo \textit{Unlit/Color} en tono rojo puro; al usar un shader sin cálculo de luces (\textit{Unlit}), se garantiza que el láser siempre brille intensamente independientemente de las sombras o la iluminación de la obra virtual.

\section{Selección e Inspección de Elementos (BIM Data y Modo Rayos X)}
Permite identificar piezas del modelo BIM, extraer sus metadatos (categoría, nombre, atributos) y visualizarlos en una interfaz flotante. Además, incluye la capacidad de ocultar el elemento seleccionado y permitir la visión subyacente de la pieza individual.

El sistema se apoya en dos scripts principales: \texttt{BIMElementSelector} y \texttt{VRUIManager}. El selector lanza un rayo físico filtrado por una \texttt{LayerMask}. Cuando el rayo colisiona con un objeto, se activa un sistema de feedback visual (cambio de color a amarillo para el hover y cian para la selección). Los objetos BIM importados suelen contener información en su nombre de jerarquía. El script fragmenta el nombre del objeto para reconstruir una ficha técnica con formato HTML compatible con \texttt{TextMeshPro}.

El \texttt{VRUIManager} se encarga de posicionar el panel de información. Mediante cálculos vectoriales, el panel se sitúa siempre a 1.2 metros frente al usuario y orientado hacia su cabeza, evitando que el texto se vea deformado o quede oculto tras muros.

Se ha implementado un método \texttt{HideSelectedElement()} que añade el objeto seleccionado a una lista de "ocultos" y lo desactiva. El sistema permite la reversibilidad mediante un método de restauración total vinculado al botón de agarre (Grip).

El script \texttt{BIMElementSelector} se añadió al objeto \texttt{OVRControllers}. En el Inspector, se asignó el LeftControllerAnchor como origen del rayo y se vinculó la referencia del \texttt{VRUIManager}. \subsection{Inteligencia Espacial y Prevención de Oclusiones (Anti-Clipping)}
Desplegar menús flotantes (\textit{World Space Canvases}) a una distancia fija de 1.2 metros presentaba un alto riesgo de oclusión: si el usuario inspeccionaba una tubería cercana a una pared, la interfaz atravesaba el muro físico, imposibilitando la lectura (\textit{clipping}).

Para dotar a la interfaz de consciencia espacial, el gestor \texttt{VRUIManager} implementa un algoritmo de posicionamiento de seguridad dinámico. Antes de invocar el panel, el sistema traza un rayo de detección (\texttt{Physics.Raycast}) desde la cámara del usuario hacia la coordenada ideal del menú, filtrando de forma excluyente las capas estructurales (\texttt{capasObstaculos}). Si se detecta una intersección geométrica (un muro) en la trayectoria, el sistema acorta el vector de distancia, reubicando el lienzo justo antes del punto de impacto (\texttt{hit.distance - margenSeguridad}). Adicionalmente, se garantiza que el lienzo nunca rebase una distancia mínima de seguridad (\texttt{distanciaMinima}) respecto a los ojos, evitando la fatiga visual por enfoque cercano (\textit{Vergence-Accommodation Conflict}).

\section{Herramienta de Medición Espacial (Cinta Métrica)}
Para evaluar las discrepancias entre el diseño teórico y la realidad construida, el usuario necesita una herramienta capaz de medir distancias euclidianas exactas en el espacio 3D. Esta "cinta métrica virtual" debe permitir seleccionar dos puntos arbitrarios en el entorno (ya sea sobre la malla BIM o sobre la nube de puntos del Gaussian Splatting) y calcular la distancia real entre ellos.

El script \texttt{VRMeasurementTool} gestiona esta funcionalidad utilizando una máquina de estados finitos basada en el número de interacciones (\texttt{clickCount}):
\begin{enumerate}
    \item \textbf{Estado Inicial (0 clics):} Un \texttt{LineRenderer} secundario actúa como láser rojo de apuntado, proyectándose constantemente desde el mando para indicar el punto exacto de colisión mediante un \texttt{Physics.Raycast} filtrado por una máscara de capas (\textit{LayerMask}) para ignorar la interfaz de usuario.
    \item \textbf{Primer Punto (1 clic):} Al pulsar el gatillo derecho, se registra la coordenada espacial (\texttt{pointA = hit.point}). Se activa la "cinta métrica" (un \texttt{LineRenderer} principal). Un extremo se ancla en \texttt{pointA} y el otro sigue dinámicamente la posición actual del láser de apuntado.
    \item \textbf{Segundo Punto (2 clics):} Al pulsar de nuevo, la medición se fija. Se utiliza la función matemática nativa \texttt{Vector3.Distance(start, end)} para obtener la longitud exacta. En este mismo instante, la medida formateada se inyecta en la estructura de datos persistente (\texttt{GeneradorPDF.medidasRealizadas}) para su posterior inclusión automática en el informe de auditoría.
    \item \textbf{Generación Dinámica de UI:} Para mostrar el resultado, el script instancia un GameObject flotante con un componente \texttt{TextMeshPro} posicionado en el punto medio exacto geométrico (\texttt{midPoint}) entre ambas coordenadas.
\end{enumerate}


Para su implementación, se asignó el script \texttt{VRMeasurementTool} al objeto gestor de interacciones de las manos \texttt{OVRControllers}.
En el Inspector, se configuró la variable \texttt{Measurement Mask} en \texttt{Everything}. Permite que el Raycast colisione tanto con los \texttt{MeshColliders} del modelo BIM como con los colisionadores de la reconstrucción volumétrica.


\section{Sistema de Auditoría y Trazabilidad (Incidencias)}
Más allá de la visualización, la aplicación debe permitir al usuario señalar los errores encontrados durante la inspección. Esta funcionalidad permite "clavar" marcadores visuales en el entorno 3D, categorizándolos según su nivel de gravedad (Grave, Leve o a Revisar) mediante un flujo de trabajo adaptado a la Realidad Virtual.

El sistema se centraliza en el script \texttt{VRIssueTracker.cs} diseñado específicicamente para entornos inmersivos:

Para no saturar la visión del usuario con interfaces gráficas intrusivas, se implementó un sistema de selección mediante el Joystick secundario. Al iniciar la creación de una incidencia, la lectura del eje \texttt{OVRInput.Axis2D.SecondaryThumbstick} determina el color y la categoría del marcador (Arriba para Grave/Rojo, Izquierda para Leve/Amarillo, Derecha para Revisar/Azul).

Para asegurar la legibilidad constante de la información adjunta a estas marcas, independientemente del ángulo de aproximación del operador, se implementó una rutina geométrica de orientación continua (\textit{Billboarding}). El script \texttt{BillboardText} fuerza la rotación del elemento textual para encararlo contra el vector de la cámara del usuario (\texttt{LookAt()}).

Para integrarlo en Unity, el script se acopló al ancla del controlador derecho (\texttt{RightControllerAnchor}). Posteriormente se vincularon las entradas lógicas a los botones físicos: el Botón A (\texttt{OVRInput.Button.One}) funciona como disparador y confirmador (doble estado).

\section{Sistema de Gestión de Capas Estructurales (BIM Layer Manager)}
En la auditoría de proyectos constructivos, es habitual que los elementos arquitectónicos superficiales (como muros o falsos techos) oculten las instalaciones críticas (tuberías, cableado, estructura portante). El objetivo de esta funcionalidad es proporcionar al usuario una herramienta de "deconstrucción virtual", permitiéndole aislar, ocultar o mostrar grupos enteros de elementos del modelo BIM clasificados por su tipología constructiva más allá de la manera manual anteriormente comentada.

Para desarrollar esta mecánica, se ha implementado un sistema compuesto por dos scripts interdependientes: \texttt{BuildingLayerManager} y \texttt{MenuController}.


El gestor principal \texttt{BuildingLayerManager} utiliza una clase serializada \texttt{BuildingLayer} que actúa como contenedor lógico. Esta clase asocia un nombre de categoría legible (ej. "Muros", "Suelos") con una lista dinámica de GameObjects (los elementos 3D individuales). Para evitar desincronizaciones de estado al arrancar la aplicación, el método \texttt{Start()} inspecciona la visibilidad real del primer objeto de cada lista en la jerarquía y ajusta la variable booleana \texttt{isVisible} en consecuencia. Se ha desarrollado un método público \texttt{ToggleLayer(string name)} que itera sobre la lista correspondiente e invierte su estado activo mediante la función nativa \texttt{SetActive()}. Adicionalmente, se implementaron métodos de control global \texttt{(ShowAll} y \texttt{HideAll}) que fuerzan un estado uniforme en todas las capas registradas, facilitando el reinicio rápido del entorno.

Debido a la limitación de botones físicos en los controladores de realidad virtual, se delegó el control de estas capas a un panel de interfaz gráfica bidimensional inmersiva. El script \texttt{MenuController} se encarga de interceptar la pulsación del botón primario del mando izquierdo para alternar la visibilidad de este panel, liberando así los comandos físicos para otras herramientas.

Los modelos BIM exportados en formatos estándar (como IFC o FBX) a menudo fragmentan las geometrías asignándoles identificadores únicos (ej. 0x2372c). Para solventarlo, se creó un objeto vacío denominado \texttt{[BuildingManager]}. Utilizando la función de bloqueo del Inspector (Lock), se seleccionaron en bloque los objetos de la jerarquía correspondientes a una misma tipología y se asignaron de manera manual a sus listas correspondientes en el componente \texttt{BuildingLayerManager}.
Se diseñó un panel flotante en el Canvas principal que incluye botones interactivos (UI Buttons) para cada capa registrada, así como para los controles maestros ("Mostrar Todo" y "Ocultar Todo").
Mediante el sistema de eventos de Unity \texttt{OnClick()}, cada botón de la interfaz se vinculó al objeto \texttt{[BuildingManager]}. A los botones individuales se les asignó la función dinámica \texttt{ToggleLayer} pasando el nombre exacto de la capa como parámetro de cadena de texto (string), mientras que a los botones maestros se les asignaron las funciones directas \texttt{ShowAll} y \texttt{HideAll}. \section{Arquitectura de Navegación Multi-Escena e Interfaz Responsiva}
Para dotar a la aplicación de una estructura escalable, se ha implementado un sistema de gestión de escenas que permite al usuario seleccionar entre diferentes modelos de auditoría desde una sala central. El objetivo técnico es garantizar una navegación fluida y una interacción con los menús que sea visualmente coherente y que no interfiera con las herramientas de medición o selección de elementos BIM.


\begin{itemize}
\item \texttt{SceneLoader.cs}: Utiliza el espacio de nombres \texttt{UnityEngine.SceneManagement} para ejecutar transiciones asíncronas entre mapas. Se ha implementado una lógica de preprocesador \texttt{\#if UNITY\_EDITOR} para permitir el cierre controlado de la aplicación tanto en el entorno de desarrollo como en el dispositivo Meta Quest de forma nativa.
\item Para evitar el problema del "Click-Through" (activar herramientas de medición al interactuar con el menú), se ha modificado la lógica de los scripts \texttt{VRMeasurementTool} y \texttt{BIMElementSelector}. Mediante el uso de LayerMasks y comprobaciones de colisión en la capa "UI", el sistema detecta si el láser impacta en la interfaz; de ser así, se levanta una "bandera" (booleana) que inhabilita las funciones de los gatillos para la manipulación del modelo, delegando el input exclusivamente a la navegación de la interfaz de usuario.
\item Corte Visual del Puntero (\texttt{ControllerRayVisual}): Se ha sustituido el trazado de línea estático por un sistema dinámico basado en \texttt{Physics.Raycast}. El láser ahora calcula en cada frame la distancia al primer objeto sólido (botón o muro), ajustando el extremo del LineRenderer al punto exacto de impacto, lo que elimina la desorientación visual que produce un láser atravesando interfaces físicas.
\end{itemize}

La implementación en el motor gráfico requirió una reconfiguración de los módulos de entrada de Oculus (OVR). Se sustituyó el sistema de entrada estándar por el \texttt{OVR Input Module}, vinculando el "Ray Transform" al mando derecho. Los Canvas de los menús se configuraron en modo World Space con un componente OVR Raycaster para procesar los eventos de los mandos táctiles.

Para que los botones fueran detectables por el sistema de físicas y por el láser visual, se les dotó de componentes Box Collider ajustados a sus dimensiones. Se configuró una transición de color (Color Tint) en los botones para proporcionar feedback visual inmediato (Highlight, Pressed) al usuario, tal como se ilustra en la Figura~\ref{fig:interfaz-menu}.

\section{Experiencia de Usuario (UX) y Animaciones Procedurales en VR}
En el desarrollo de aplicaciones de Realidad Virtual, los cambios bruscos en el entorno o en las interfaces (efecto \textit{pop-in}) pueden romper la inmersión del usuario e incluso inducir cinetosis (mareo virtual). Para mitigar estos efectos, se implementó un sistema de animaciones procedurales basadas en interpolación matemática (\textit{Tweening}) y transiciones de estado.

El suavizado de las interfaces de usuario se programó empleando Corrutinas (\texttt{IEnumerator}) nativas de Unity. En scripts como \texttt{VRUIManager} y \texttt{MenuController}, la aparición y desaparición de los paneles no se realiza mediante un simple cambio booleano de activación, sino alterando gradualmente la propiedad \texttt{transform.localScale} del \texttt{GameObject} desde un vector nulo \texttt{(0,0,0)} a su escala original. Para dar a esta animación un aspecto orgánico, se implementó una curva matemática de desaceleración (\textit{Ease-Out}) calculada mediante la fórmula $t = t \times (2 - t)$, donde $t$ representa el tiempo normalizado de la transición.

Esta técnica de interpolación también se aplicó a la ocultación de las piezas del modelo BIM y a la transición cruzada entre el modelo teórico BIM y el renderizado de \textit{Gaussian Splatting} gestionado por el \texttt{LayerSwitcher}, donde el modelo saliente se reduce de forma progresiva mientras el entrante recupera su escala original.

En cuanto a la interacción directa con la interfaz, se detectaron deficiencias visuales al utilizar los cambios de color predeterminados de la UI de Unity en Realidad Virtual. Para solventarlo, se implementó el script \texttt{BotonMaterialVR}, el cual hereda de las interfaces de eventos del puntero (\texttt{IPointerEnterHandler}, \texttt{IPointerDownHandler}, etc.). En lugar de aplicar un tinte de color bidimensional, el sistema sustituye el material completo (\textit{Material Swapping}) del componente renderizado en respuesta a los estados de interacción (Hover, Pressed). Esta solución garantiza que los botones mantengan sus propiedades de sombreado e iluminación tridimensional (shaders), mejorando la respuesta táctil visual (\textit{feedback}).

Para la carga entre escenas de la aplicación, el script \texttt{SceneLoader} fue ampliado para incorporar un fundido a negro (\textit{Fade-to-Black}). Se añadió un objeto \texttt{Canvas} configurado en \textit{World Space} y anclado rígidamente a escasos centímetros de la cámara del usuario (\texttt{CenterEyeAnchor}), asegurando la oclusión total del campo de visión sin generar distorsiones geométricas de perspectiva. La manipulación de su componente \texttt{CanvasGroup.alpha} se sincronizó con el método \texttt{SceneManager.LoadSceneAsync()}. A diferencia de las cargas síncronas convencionales, las operaciones en segundo plano evitan que el hilo principal del procesador se congele al cambiar de mapa, garantizando que el \textit{tracking} (seguimiento de la cabeza) de las gafas se mantenga fluido y no expulse al usuario de la experiencia inmersiva.

\subsection{Persistencia de Datos en Menú Principal}
Para dotar a la aplicación de un seguimiento temporal de las auditorías sin incurrir en el coste computacional de bases de datos relacionales, se ha implementado un módulo de persistencia ligera (\texttt{GestorFechasMenu}). El sistema hace uso del registro local del motor (\texttt{PlayerPrefs}) para guardar, leer y actualizar las cadenas de texto (\textit{strings}) correspondientes a la fecha de la última inspección de cada maqueta. Estos datos se inyectan en tiempo de ejecución en los componentes de interfaz (\texttt{TextMeshPro}), otorgando al usuario un control de registro de versiones visual desde el inicio de la aplicación.

\subsection{Gravedad Dinámica y Prevención de Cinetosis en Desniveles}
El desplazamiento continuo mediante el \textit{joystick} (\texttt{VRContinuousMovement}) es fundamental para recorrer maquetas a escala real. Sin embargo, los sistemas de movimiento estándar presentan deficiencias matemáticas al interactuar con desniveles negativos (bajada de escaleras). Al avanzar horizontalmente a mayor velocidad que la aceleración gravitatoria, el \texttt{CharacterController} pierde contacto superficial, generando micro-saltos y caídas abruptas que inducen cinetosis grave en el visor.

Para subsanar esta irregularidad computacional, se aisló el procesamiento del vector de movimiento horizontal (\texttt{X, Z}) del vertical (\texttt{Y}). El sistema evalúa constantemente la propiedad \texttt{isGrounded}. Cuando el usuario se encuentra en contacto con una superficie (como el borde de un escalón), en lugar de aplicar una aceleración gravitacional acumulativa, el algoritmo inyecta una fuerza descendente constante e intencionada (\texttt{-2f}). Esta presión vertical actúa como un anclaje magnético, obligando a la cápsula de colisión a adherirse milimétricamente a la pendiente de las escaleras, garantizando un descenso completamente fluido e inmersivo.




\section{Sistema de Recorridos Cinemáticos Automatizados}
Con el fin de facilitar la presentación y documentación de los proyectos arquitectónicos, se desarrolló un sistema de "vuelo de dron" que permite al usuario experimentar un recorrido guiado y suavizado a través de las instalaciones de forma pasiva.

Técnicamente, este módulo se apoya en el paquete oficial \textbf{Cinemachine 3} y su integración con el nuevo marco de trabajo \textbf{Unity Splines}. En la escena virtual, se dibujó un trayecto físico empleando un contenedor \texttt{SplineContainer}, donde un componente \texttt{Spline Smoother} se encarga de interpolar curvaturas de tipo Bézier entre los distintos puntos de paso (\textit{Knots}), evitando giros abruptos en las esquinas de los pasillos de la obra, tal como se puede apreciar en la Figura~\ref{fig:recorrido}.

La adaptación de este sistema de cámaras a la Realidad Virtual presentó un desafío de arquitectura de software. En el desarrollo tradicional, Cinemachine toma el control directo del \texttt{Transform} de la cámara principal. Sin embargo, en un entorno inmersivo, el SDK de Meta fuerza la actualización constante de la posición de las cámaras para reflejar el movimiento físico de la cabeza del usuario. Si dos sistemas intentan controlar el mismo objeto simultáneamente, se produce una discordancia de \textit{tracking}.

Para solventar esta incompatibilidad, se programó el script \texttt{DroneTourController}. En lugar de utilizar componentes automatizados como \texttt{CinemachineBrain}, el script evalúa manualmente la Spline matemática. En la función \texttt{Update()}, se utilizan los métodos de la API de Unity \texttt{EvaluatePosition} y \texttt{EvaluateTangent} para extraer la coordenada tridimensional y el vector director correspondientes al porcentaje de progreso actual de la ruta.

Estos datos matemáticos se aplican directamente al objeto raíz del jugador (el \texttt{[BuildingBlock] Camera Rig}), desplazando físicamente al usuario completo en lugar de secuestrar su visión, lo que le permite seguir mirando libremente a su alrededor mientras avanza. Para prevenir desorientación, el vector de rotación se proyecta sobre el plano horizontal anulando su componente vertical (\texttt{Y = 0}), garantizando que el usuario jamás vuelque hacia arriba o abajo, manteniendo el horizonte paralelo al suelo real en todo momento. Simultáneamente, el controlador deshabilita temporalmente los módulos de físicas (\texttt{CharacterController}) y las entradas manuales de los joysticks (\texttt{VRContinuousMovement}) durante el transcurso del vuelo para evitar interferencias en el movimiento espacial, restaurándolos automáticamente al concluir el trayecto.

Este sistema se divide en dos componentes principales: una cámara virtual inmersiva y un motor automático de generación documental.

\subsection{Cámara Virtual y Captura de Evidencias}
Para documentar visualmente las discrepancias estructurales o colisiones MEP encontradas durante la auditoría, se implementó una herramienta de cámara virtual interactiva gestionada por \texttt{VRCameraTool}.

El sistema renderiza la perspectiva de una cámara secundaria, simulando un dispositivo móvil anclado a la mano del usuario, proyectando la imagen en tiempo real sobre una textura dinámica (Figura~\ref{fig:camara}). Al accionar el disparador del controlador, el algoritmo lee el búfer de píxeles bidimensional de dicha textura (\texttt{Texture2D.ReadPixels}), lo codifica matemáticamente al estándar PNG (\texttt{EncodeToPNG()}) y lo almacena de forma persistente en la memoria de almacenamiento del visor (\texttt{Application.persistentDataPath}). Para maximizar la inmersión y proporcionar confirmación háptica-visual al usuario, el proceso invoca un \textit{shader} superpuesto a la lente que interpola su canal alfa para simular el destello (\textit{flash}) de una cámara tradicional.

\subsection{Motor de Generación Documental (BIM Report)}
La exportación de los datos recopilados durante la sesión de auditoría se automatizó mediante el script \texttt{GeneradorPDF}, apoyándose en la librería externa \texttt{iTextSharp}. La integración de esta librería (específicamente la versión autónoma 5.5.10) requirió reconfigurar el nivel de compatibilidad de la API del proyecto a \texttt{.NET Framework} en los ajustes del motor, posibilitando el acceso a las librerías de escritura profunda del sistema operativo requeridas para generar documentos complejos.

El diseño del generador sigue un patrón estructural basado en datos estáticos globales que actúan como "buzones". Todas las herramientas de la aplicación (inspección BIM, cinta métrica, escáner volumétrico y controlador cinemático) operan de forma independiente, pero envían sus lecturas en tiempo real a estas listas y variables centralizadas (como \texttt{elementosBIMInspeccionados} o \texttt{conflictosDetectados}). Al invocar la compilación del informe mediante la interfaz, el sistema lee esta memoria unificada y maqueta el documento que se puede observar en la Figura~\ref{fig:informe-diseño}.

A nivel algorítmico y de presentación de datos, se afrontaron los siguientes problemas.

Para evitar que los títulos descriptivos de las capturas fotográficas quedasen aislados de sus respectivas imágenes debido a los saltos de página generados por el procesador de texto interno, se encapsuló dinámicamente cada par "Título-Imagen" dentro de un objeto \texttt{PdfPTable} de una sola celda. Al activar la propiedad de diseño algorítmico \texttt{KeepTogether = true}, el sistema garantiza que el bloque se traslade íntegramente a la página posterior en caso de falta de espacio.

Tras concluir la escritura del búfer binario y cerrar el flujo de datos (\texttt{Document.Close()}), el script ejecuta un ciclo de purga (\texttt{Clear()}) sobre todas las colecciones estáticas y reinicia los contadores. Esto garantiza la estabilización de la memoria RAM del visor y habilita la realización de múltiples auditorías independientes sin requerir el reinicio completo de la aplicación de Realidad Virtual.

\section{Escáner de Desviaciones Espaciales (Mapa de Calor)}
Una de las aportaciones más innovadoras de la aplicación es la capacidad de auditar la precisión de la construcción física frente al modelo teórico BIM en tiempo real mediante un escáner de desviaciones. Esta herramienta proyecta un mapa de calor sobre las superficies del edificio virtual, marcando en color verde las áreas donde la obra real coincide con el plano, y en color rojo las zonas donde existen discrepancias geométricas, habiendo niveles intermedios.

El principal desafío técnico para implementar esta funcionalidad residía en la cantidad de detalle y datos que tenía el modelo de la realidad. El renderizador de \textit{Gaussian Splatting} procesa millones de elipsoides directamente en la Unidad de Procesamiento Gráfico (GPU) mediante \textit{Compute Shaders}. Estas representaciones carecen de geometría poligonal (\textit{Mesh}) y de colisionadores físicos, imposibilitando la interacción nativa con los sistemas de físicas del motor (\texttt{Physics.Raycast}). Además, intentar transferir las coordenadas de millones de elementos desde la GPU hacia la CPU en cada fotograma para calcular distancias provocaría una gran ralentización, hundiendo la tasa de fotogramas e induciendo cinetosis en el entorno de Realidad Virtual.

Para resolver esta limitación, se optó por crear una versión simplificada del modelo. La nube de puntos densa original se procesó mediante CloudCompare para generar un modelo aligerado aplicando un submuestreo espacial (\textit{Spatial Subsampling}) con una separación de 5 centímetros entre vértices. Este proceso redujo drásticamente el peso computacional de millones de coordenadas a unos pocos miles. El resultado se importó a Unity mediante un archivo de texto plano (\texttt{.txt}), el cual actúa como una matriz matemática tridimensional ultra-ligera gestionada por el script \texttt{ComparadorRealidad}.

\subsection{Algoritmo de Comparación Directa}
El núcleo de procesamiento de la herramienta reside en el método \texttt{ExisteRealidadCercaDe()}. Durante la fase de inicialización (\texttt{Awake}), el sistema carga las coordenadas del archivo \texttt{.txt} en la memoria RAM del visor de forma asíncrona. Cuando el usuario interactúa con la herramienta, el algoritmo realiza una búsqueda euclidiana directa en tiempo real:
\begin{itemize}
    \item Se transforma cada coordenada evaluada desde su espacio local al espacio global de la escena mediante el método \texttt{transform.TransformPoint()}. Esto permite que la nube holográfica invisible se escale, rote o traslade dinámicamente en el Inspector sin requerir una recompilación de la matriz subyacente.
    \item Para evaluar la cercanía, se calcula el cuadrado de la magnitud del vector diferencia (\texttt{sqrMagnitude}) entre el punto de impacto sobre el modelo BIM y los puntos físicos registrados. Emplear la magnitud al cuadrado evita el coste computacional de resolver raíces cuadradas, siendo significativamente más eficiente.
    \item Si el algoritmo detecta un punto físico a una distancia inferior a la "Tolerancia de Construcción" paramétrica de la aplicación, la función retorna un valor booleano positivo, confirmando la validez topológica de la estructura.
\end{itemize}

\subsection{Sistema de Evaluación Espacial Gradual}
El concepto inicial de validación binaria (correcto/incorrecto) evolucionó hacia un sistema de evaluación gradual que proporciona mayor fidelidad técnica sobre el estado de la construcción real frente al modelo BIM. El script \texttt{ScannerDesviacionesVR} parametriza la distancia obtenida del comparador euclidiano y clasifica el impacto topológico en cuatro umbrales visuales, modificando dinámicamente el material (\textit{Material Swapping}) de la marca proyectada:
\begin{itemize}
    \item \textbf{Verde (Perfecto):} La desviación es inferior al milímetro (\texttt{< 0.01m}). El elemento físico se encuentra exactamente donde dictan los planos.
    \item \textbf{Amarillo (Aceptable):} Desviación leve dentro de las tolerancias de obra (\texttt{< 0.05m}).
    \item \textbf{Naranja (Desviación Notable):} Discrepancia estructural que requiere revisión técnica (\texttt{< 0.10m}).
    \item \textbf{Rojo (Fallo Crítico):} Ausencia total del elemento físico o desviación severa que supera el umbral máximo tolerado.
\end{itemize}
Esta categorización no solo enriquece el \textit{feedback} visual en el visor VR, sino que alimenta de forma paralela las estructuras de datos estáticas (\texttt{GeneradorPDF.puntosEscaneoCorrectos} y \texttt{puntosEscaneoDesviados}) para su posterior volcado cuantitativo en el informe de auditoría.
